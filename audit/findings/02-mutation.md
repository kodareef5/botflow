# Scope 02 — Board mutation & filesystem writes

Audited: `src/core/{mutate,ops,write,template,config,emit,scheduling,refs,analyze,metrics,query,docs,presentation,index}.ts`, with call-chain reads of `load.ts`, `ids.ts`, `yaml.ts`, `card.ts`, `body.ts`, `frontmatter.ts`, `fields.ts`, `model.ts`, and the pull-side guard in `src/cli/remote.ts`. All PoCs were run as throwaway scripts under /tmp against the real source (Node 24 type-stripping); no project files were modified. Existing suites `test/security-core.test.ts`, `test/mcp-security.test.ts`, `test/remote-security.test.ts` pass (59/59).

## F02-1: Mutation writes follow committed symlinks out of the board (cards/ dir, .botflow root, initBoard clobber)
- Severity: Medium
- CWE: CWE-59 (Improper Link Resolution Before File Access), CWE-22 (Path Traversal)
- Location: src/core/mutate.ts:140-148 (`atomicWrite`/`writeCard`), src/core/mutate.ts:150-158 (`initBoard`), src/core/mutate.ts:110-137 (lock file); contrast with the read-side guard at src/core/load.ts:36-58
- Description: The read path deliberately skips symlinks (`readBoardDocuments` uses `lstat` at every level; the comment at load.ts:36-39 says a committed symlink is "silently skipped instead of exfiltrated"). The write path has no equivalent guard: `writeCard` does `writeFileSync(tmp)` + `renameSync(tmp, join(root, card.file))`, and both calls follow symlinks in every *directory* component of the path. So:
  - If a cloned repo carries `.botflow/cards` as a symlink to an absolute directory, the board loads cleanly (0 cards — the symlinked dir is skipped on read, so nothing looks wrong), and the next `botflow add` (or any op that creates a card: quick-add, promote, close-with-recurrence, transfer) writes a new file into the attacker-chosen directory.
  - If `.botflow` itself is a symlink to a directory without `board.yaml`, `initBoard` proceeds and writes `board.yaml`, `cards/`, and — unconditionally, no collision check — overwrites an existing `.gitignore` at the target (`writeFileSync`, not `atomicWrite`, and no `existsSync` gate).
  - `withBoardLock` also creates `board.lock` through a symlinked root.
- Exploit scenario: Attacker publishes a repo containing `.botflow/board.yaml` and `.botflow/cards -> /Users/<anyone>/.ssh` (or `~/.config`, or another project dir). Git materializes committed symlinks on clone. The victim (or an AI agent driven by the repo's AGENTS.md/README prompt injection, or MCP `add` tool calls) runs an ordinary `botflow add "…"`. A file `001-<slug>.md` with fully attacker-influenced content (title, and body via `--body`/MCP) lands in the victim's directory. The planted name is deterministic (`001-…` on the empty-seeming board, slug charset `[a-z0-9-]`, `.md` suffix), and the `existsSync` collision check prevents overwriting an existing same-named file, so the primitive is *create-only* for cards — but `initBoard`'s `.gitignore` write is a genuine clobber of an existing file.
- Evidence: PoC (`/tmp/bf-poc1.ts`): symlinked `.botflow/cards -> /tmp/bf-poc1/victim-dir`; `loadBoard` saw 0 cards, then `addCard(...)` succeeded and `readdirSync(target)` showed `001-planted-by-prompt-injection.md` with full card content next to the pre-existing `KEEPME.txt`. PoC (`/tmp/bf-poc6.ts`): `.botflow -> other-project/` symlink; `initBoard` succeeded and the target's pre-existing `.gitignore` (`node_modules\ndist\n`) was overwritten with `index.db\nindex.db-*\nboard.lock\n`.
- Suggested fix: Reuse the pull-side pattern that already exists at src/cli/remote.ts:124-141 (`assertContainedTargets`): before any mutation write, (a) reject a symlinked board root (`lstatSync(root).isSymbolicLink()`), and (b) for `join(root, card.file)`, walk each existing ancestor dir under `root` with `lstat` and refuse symlinks (or compare `realpathSync(dirname(target))` against `realpathSync(root)`). Add the same root check to `initBoard`, and make its `.gitignore`/`board.yaml` writes conditional on non-existence. Zero-dependency; all `node:fs`.

## F02-2: Cross-board link/transfer escape via committed symlink — nesting check is purely lexical
- Severity: Low
- CWE: CWE-59 (Improper Link Resolution Before File Access)
- Location: src/core/mutate.ts:214-223 (`mutateRelation`), src/core/mutate.ts:346-353 (`transferCard`)
- Description: Both operations resolve a user-supplied target (`sub#005` / target dir) with `resolveBoardRoot(resolve(sourceRoot, ref))` and then enforce "target board must be nested inside the source project tree" via `relative(sourceRoot, targetRoot)` — a purely lexical computation. `resolveBoardRoot` uses `existsSync`, which follows symlinks, and neither side calls `realpathSync`. A committed symlink inside `.botflow/` (e.g. `.botflow/sub -> /abs/path/to/other-project`) therefore passes the check: `relative()` sees the lexical path `sub/.botflow`, happily "inside".
- Exploit scenario: Malicious repo ships `.botflow/sub -> <absolute path of another botflow board on the victim's machine>`. Victim (or an agent via CLI/MCP) runs `botflow card link 001 sub#005` or `botflow card copy 001 .botflow/sub`. `linkCards` appends a forged relation + log entry to a card of the external board; `transferCard` writes a complete attacker-controlled card file (title, body, labels, extras) into the external board's `cards/` dir. Preconditions are real: the attacker must guess an absolute path that exists on the victim's machine *and* contains a botflow board (and, for link, the target card id). That targetability constraint is why this is Low rather than Medium. Note the symlink needs no cooperation from the target board, and the board.lock for the "target" is also created through the link.
- Evidence: PoC (`/tmp/bf-poc2.ts`): with `.botflow/sub -> /tmp/bf-poc2/other-project`, `linkCards(root,'001','sub#005','relates','mallory')` succeeded; the victim board's `005-real.md` gained `relations: [{type: relates, target: ../..#001}]` and a `mallory: linked relates ../..#001` log line. `transferCard(root, '.botflow/sub', '001', 'mallory')` then wrote `cards/006-trap.md` into the victim board.
- Suggested fix: After the lexical check, compare canonical paths: `realpathSync(targetRoot)` must equal or be under `realpathSync(sourceRoot)` (plus the one-parent workspace allowance used in `loadTree`). Fail with a UsageError on symlinked intermediates, matching F02-1's guard.

## F02-3: Windows cross-drive / UNC targets bypass the "nested inside" check
- Severity: Low
- CWE: CWE-22 (Path Traversal)
- Location: src/core/mutate.ts:221 and src/core/mutate.ts:351 (`relative(sourceRoot, targetRoot)` checks)
- Description: The escape check is `targetPath === '..' || targetPath.startsWith('..' + sep)`. On Windows, `path.relative()` across drives (or to a UNC share) returns an *absolute* path (`D:\other\.botflow`, `\\server\share\…`), which passes both tests. `validateBoardPath` (ops.ts:119-134) does reject drive-letter and UNC-absolute board paths, but `mutateRelation`/`transferCard` never apply it to the resolved *target* — they rely solely on the `relative()` result. So on Windows, a relation boardRef like `D:\other#001` (or a transfer target on another drive) escapes the nesting invariant entirely.
- Exploit scenario: Windows victim; attacker-influenced CLI/MCP input names a board on another drive/share (`botflow card copy 001 D:\victim-project`). The target board must exist with a parseable board.yaml (same precondition as F02-2). Demonstrated the check gap on macOS via `path.win32.relative('C:\\repo\\.botflow','D:\\other\\.botflow')` → `'D:\\other\\.botflow'`, which passes both `..` tests; full exploitation not executed (no Windows host here), hence Low.
- Evidence: `win32.relative('C:\\repo\\.botflow', 'D:\\other\\.botflow')` → `"D:\\other\\.botflow"`; `!(rel === '..' || rel.startsWith('..' + win32.sep))` → `true` (passes).
- Suggested fix: Add `isAbsolute(targetPath)` (platform-specific) to the rejection condition in both places — one line each: `if (targetPath === '..' || targetPath.startsWith(\`..${sep}\`) || isAbsolute(targetPath))`.

## F02-4: Self-referential board symlink deadlocks cross-board ops until lock timeout
- Severity: Low
- CWE: CWE-667 (Improper Locking) / CWE-400 (Uncontrolled Resource Consumption)
- Location: src/core/mutate.ts:214-224 with src/core/mutate.ts:333-337 (`withBoardLocks`) and src/core/mutate.ts:88-106 (`reapStaleLock`)
- Description: `withBoardLocks([sourceRoot, targetRoot])` dedupes/sorts by *lexical* resolved path. A committed symlink `.botflow/self -> .` makes `resolveBoardRoot('.botflow/self')` a second, lexically distinct root for the same physical directory. Acquiring the second `openSync(lock, 'wx')` then hits `EEXIST` — but the lock file contains the *current process's own pid*, which is alive, so `reapStaleLock` deliberately never reaps it. The operation spins for `BOTFLOW_LOCK_TIMEOUT_MS` (default 5s) and fails with "board is locked by another process".
- Exploit scenario: Malicious repo ships `.botflow/self -> .`; an agent following repo instructions (or exploring relations) runs `botflow card link 001 self#001` → 5-second hang, then error, every time. Availability nuisance limited to cross-board verbs; no data corruption (the lock did its job, against itself).
- Evidence: PoC (`/tmp/bf-poc5.ts` part b): `linkCards` with a `self -> .` symlink threw after 5007 ms: `board is locked by another process (/tmp/.../self/board.lock)`.
- Suggested fix: In `withBoardLocks`, dedupe by `realpathSync(root)` rather than `resolve(root)`; optionally treat "lock owner pid === process.pid" as re-entrant success (the process already holds the flock-equivalent semantics of having created it).

## F02-5: `__proto__` YAML keys hit the prototype setter — config keys hidden from lint, silently rewritten away
- Severity: Low
- CWE: CWE-1321 (Improperly Controlled Modification of Object Prototype Attributes — limited, non-global variant)
- Location: src/core/yaml.ts:15 (`KEY_RE` allows `__proto__`), src/core/yaml.ts:132-166 (`parseEntry` does `obj[key] = value` on a `{}` literal); consumed by src/core/config.ts:179-276 and src/core/write.ts:46 / src/core/emit.ts:36-84
- Description: `__proto__` matches the key regex, and `obj['__proto__'] = <map>` invokes the `Object.prototype.__proto__` setter, so the value becomes the parsed object's *prototype* instead of an own property. Consequences measured on board.yaml: (a) known keys (`name`, `ids`, `lanes`, …) are then read through the prototype chain by `parseBoardConfig` — they take effect but produce **zero findings**, including suppressing the mandatory "name is required" schema error, and they bypass the duplicate-key check (`Object.hasOwn` never sees them); (b) `Object.keys()`-based preservation (`config.extra`, card `extra`) never sees the block, and the first `emitBoardYaml` rewrite (saveFilter/subscribeLane/removeFilter) silently normalizes it into real keys or drops unknown sub-keys entirely. No global `Object.prototype` pollution occurs (verified: `({})['name']` stays `undefined`), so this is audit-trail evasion + silent data loss, not RCE-class pollution. Primary ownership is the parser (wave 01); recorded here because the mutation-side rewrite is where the silent loss lands.
- Exploit scenario: A malicious repo ships `board.yaml` with a `__proto__:` block (e.g. smuggling `ids: hash` or an extra lane). Reviewers and `botflow lint` see a clean file — the unknown-key/preserved findings that would flag unusual config never fire — while the smuggled config is operative. On the next config rewrite the block vanishes or mutates the file in ways the diff reader didn't expect.
- Evidence: PoC (`/tmp/bf-poc4.ts`): `parseYaml('botflow: 0\n__proto__:\n  name: smuggled-name\n  ids: hash\n')` → own keys `[ 'botflow' ]`; `parseBoardConfig` returned `name: "smuggled-name", ids: "hash"` with **empty findings**; `emitBoardYaml` output contained neither `__proto__` nor any unknown-key trace.
- Suggested fix: In `yaml.ts parseEntry`, reject or neutralize dangerous keys: `if (key === '__proto__' || key === 'constructor' || key === 'prototype') throw new YamlError(...)`, or build maps with `Object.create(null)` and convert at the boundary. Cheap and zero-dependency.

## F02-6: Oversized numeric card id crashes every subsequent `add` with raw ENAMETOOLONG
- Severity: Low
- CWE: CWE-400 (Uncontrolled Resource Consumption) / CWE-248 (Uncaught Exception)
- Location: src/core/ids.ts:5-16 (`nextSeqId`, unbounded BigInt growth), src/core/ops.ts:504 (filename construction), src/core/mutate.ts:140-144 (`atomicWrite` lets the errno escape)
- Description: `nextSeqId` takes `max(existing numeric ids) + 1` with `BigInt`, and pads to the widest existing id. A hostile card with `id: "999…"` (300 digits, quoted so it stays a string — loads fine; `id-scheme-mismatch`/`filename-id-mismatch` are findings, not rejections) makes the next allocated id 301 digits. The resulting `cards/<301 digits>-<slug>.md` exceeds the 255-byte filename limit, and `writeFileSync` throws a raw `ENAMETOOLONG` (not a `UsageError`), crashing the command. The condition persists: every `add` on that board fails until the offending card is removed by hand.
- Exploit scenario: Malicious repo includes one such card; the victim's (or agent's) first `botflow add` dies with an uncaught stack trace. Board reads still work; `ids: hash` boards are immune. Impact is per-board availability of card creation plus a confusing error — honest Low.
- Evidence: PoC (`/tmp/bf-poc3b.ts`): loaded id length 300; `addCard` threw `Error | ENAMETOOLONG: name too long, open '/tmp/bf-poc3b/.botflow/cards/1000…000-next.md.<pid>.<rand>.tmp'`.
- Suggested fix: Cap id width in `nextSeqId` (e.g. refuse/ignore numeric ids longer than ~20 digits when computing the max — they can't be legitimate seq output), and/or have `docs.ts` treat ids above a length bound as a schema error that blocks the card. Optionally wrap fs errnos in `atomicWrite` into `UsageError` for consistent UX.

## F02-7: Unsafe-integer extras change type on rewrite (YAML emit round-trip fidelity)
- Severity: Info
- CWE: CWE-704 (Incorrect Type Conversion or Cast)
- Location: src/core/yaml.ts:230 (`parseInt` without safe-integer bound), src/core/emit.ts:20-25 (`emitScalar` emits `String(1e21)` = `1e+21`)
- Description: The parser turns any `INT_RE` match into `parseInt(s, 10)` without checking `Number.isSafeInteger`, so an unknown/preserved key with a huge integer (e.g. `priority-x: 999999999999999999999`) is stored as the imprecise number `1e21`. On rewrite, `emitScalar` emits `1e+21`, which reparses as the **string** `"1e+21"` — a silent type change in a supposedly lossless preservation path. Also note `id: 999…` (unquoted) becomes `"1e+300"` via `asIdString` (card.ts:304-307), which is why F02-6 needed a quoted id. No security impact beyond integrity noise; recorded for completeness.
- Exploit scenario: Malicious repo plants a huge integer in a preserved frontmatter key; after any mutation rewrite, the value's type/value drift — a diff the victim didn't make. Integrity nuisance only.
- Evidence: In PoC 3, unquoted `id: <300 digits>` loaded as `"1e+300"` (String of an unsafe float) instead of the literal digits.
- Suggested fix: In `parseScalar`, only return a number when `Number.isSafeInteger(parseInt(s, 10))`; otherwise keep the literal string. Emit side needs no change.

## Checked clean
- New-card filename traversal: `card.file` is built only as ``cards/${id}-${slugify(title)}.md`` with ids from `nextSeqId` (digits) / `newHashId` (CSPRNG over `[a-z0-9]`) and `slugify` stripping to `[a-z0-9-]` (src/core/ids.ts:5-36, ops.ts:504,716,1579) — `..`, `/`, NUL, drive letters all unreachable; grep confirmed these are the only `.file` assignments.
- Loaded-card rewrite paths: `card.file` comes from the `cards/` readdir walk with `lstat` at every level (load.ts:40-60); filenames cannot contain separators, so writes stay under `cards/`.
- rename-over-symlink: verified dynamically that `renameSync(tmp, path)` replaces the symlink itself, leaving its target intact — `atomicWrite`'s final component is symlink-safe (PoC 5a).
- NUL bytes: `existsSync`/`resolve` treat NUL-containing paths as nonexistent; `linkCards` with `a\0b#002` fails closed with a `UsageError`, no raw crash (PoC 3a).
- YAML emit injection: keys are constrained to `[A-Za-z0-9_-]+` by the parser (yaml.ts:15) so `emitMap`'s raw key interpolation can't be reached by hostile keys; `needsQuote`/`emitScalar` quoting covers all value metacharacters (`#`, `:`, flow chars, quotes, newlines) — round-trip tests for hostile labels/empty maps pass.
- Command execution via template instantiation: `spawnSync` argv arrays, `--` separator, dash-leading sources rejected (template.ts:34-52); git clone does not copy hooks and `.git` is removed immediately; commit identity forced via `-c`; name rewrite uses `emitScalar`.
- Log/section/attachment injection on write: `sanitizeInline`/`sanitizeActor` (colon-stripping), `sanitizeBlock` heading escaping, `sanitizeSectionName`, `sanitizeUrl` `)`-encoding — code read + covered by security-core tests (newline forgery, section splicing, actor truncation).
- ReDoS: every regex in scope is a constant pattern; the query language (query.ts) compiles no regexes — matching is `String.includes` only.
- Recursion/stack exhaustion: yaml `MAX_DEPTH` 100 (yaml.ts:104), dep-cycle DFS iterative (analyze.ts:175-224), cross-board cycle DFS iterative (analyze.ts:323-379); 5000-card chains covered by tests.
- Automation bounds: ≤16 rules per event (ops.ts:410), ≤100 actions per automation pass (ops.ts:1505-1513), board buttons capped at 100 matched cards (ops.ts:1485); quick-add re-analysis per card is quadratic only with attacker-driven input volume and bounded constants.
- Prototype pollution (global): verified `__proto__` assignment affects only the parsed object; `({}).name` unpolluted (F02-5).
- `validateBoardPath` for board-card paths: rejects absolute, drive-letter, UNC, and depth-escaping values on add/edit/transfer (ops.ts:119-134 + tests); `loadTree` never walks escaping paths (findings only).
- Board lock: `O_EXCL` creation, symlinked lock can't be followed on create, stale reaping requires a *dead* pid (live pids never age-reaped — deliberate), multi-board locks acquired in sorted order (no AB/BA deadlock between distinct real boards).
- Pull/import snapshot writes (adjacent scope): gated by `validateBoardDocuments` + `safeCardDocumentPath` + `assertContainedTargets` realpath containment (docs.ts:126-166, remote.ts:124-141) — the containment pattern F02-1/F02-2 recommend porting to the mutation path.
- Config emit raw interpolations (`lane.id`, substates, filter/rule/button ids, events, rollup enums): all validated to slugs/enums at parse (config.ts parseLanes/parseRules/etc.), so `emitBoardYaml` cannot be driven into key/line injection.
- `sameValue`/serialization of relations and extras: no type-confusion path that skips validation; `checkedRelations`/`checkedCardReferences` re-validate on every mutation; analyze's `parseCardReference(...)!` assertions are backed by parse-time validation (card.ts:103-153).
